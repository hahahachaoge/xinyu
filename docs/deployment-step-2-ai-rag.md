## 已修复的问题

- 原先 MySQL 有 40 条分块记录，而 PostgreSQL 向量表为空。现在提供“重建分块向量”和“重建全部分块向量”，基于现有文本生成真实嵌入，并回写真实 UUID。
- 生成与写入新向量成功后，才在 MySQL 事务内更新关联和完成状态；失败时保留旧分块及旧关联，并清理已生成的新向量。成功后清理旧向量，删除文档时也执行关联向量清理。跨数据库不是分布式事务，异常清理结果须通过索引检查确认。
- 批量重建按文档顺序执行，避免一次并发请求全部文档。重建现有分块保留分块 ID，已保存聊天的来源引用继续可用。
- DeepSeek 流式和非流式请求使用服务端配置的 Key。网络失败、余额不足、无效回复或未完整结束的回复会明确报错，不会保存为正常 AI 回复。
- 用户问题与完整 AI 回复在同一 MySQL 事务内保存；回复提交成功后才发出 `saved` 和 `[DONE]`。失败不会自动再发送一次非流式请求，避免重复提问和重复计费。
- 前端 SSE 解析保留跨网络分包的 JSON 和 UTF-8 文本；切换页面会取消当前请求。聊天 URL 带当前会话 ID，刷新后从数据库恢复。
- 向量检索结果按相似度顺序关联到分块，丢失的关联不作为来源返回；流式事件提供 `retrievalMode` 区分向量、关键词及无命中，当前聊天页不显示该状态标签。无资料时，提示词要求模型说明未检索到相关内容。
- 后端保留分块详情与出处查询能力。聊天页在显示时过滤片段引用并转义 HTML，原始消息及关联不因此删除。

## 评委从 GitHub 首次运行

1. 按 README 配置数据库、JWT、DeepSeek Key 和嵌入服务 Key，导入 MySQL 示例数据，启用 PostgreSQL 的 vector 扩展。
2. 按 [评委运行说明](judging-demo.md) 启动前后端演示模式，用 `admin / 12345678` 登录，角色选择管理员。
3. 进入“知识文档”管理，点击“刷新索引检查”。首次导入 SQL 只提供分块文本，不附带本地 PostgreSQL 的生成向量。
4. 点击“重建全部分块向量”。这一步使用部署者配置的嵌入服务 Key，产生相应 API 用量。等待任务结束后刷新索引检查，确认全部现有分块均匹配。
5. 用 `user / 12345678` 登录，打开 AI 问答，提问“考试前总是紧张怎么办？”或“睡眠不足如何调整作息？”，检查流式回复完成、消息保存且不显示片段编号或来源标签。
6. 刷新页面并重新登录，确认会话及消息恢复；另一个普通用户不应看到这些记录。
7. 如需复核实际检索，查看流式响应的 `chunks` 事件及 `retrievalMode`，结合管理员索引检查核对；资料出处在后台文档详情查看。仅收到文本回复不能证明使用了向量检索。

如需通过接口操作，以下接口均仅限管理员，使用登录 Token 放入 `Authorization` 请求头：

| 接口 | 请求体 | 用途 |
| --- | --- | --- |
| `POST /knowledgeDocument/indexAudit` | `{}` | 查看真实数量、缺失关联、文本差异、孤立向量与待处理文档 |
| `POST /knowledgeDocument/rebuildVectors` | `{"id":1}` | 保留已有分块并重建单篇文档向量 |
| `POST /knowledgeDocument/rebuildAllVectors` | `{}` | 顺序重建所有已有分块的文档 |

`/reVectorize` 会重新解析上传的原文件。只有原始文本分块、没有原文件时，应选择“重建分块向量”。后续更新文档内容需要上传新原文件。
